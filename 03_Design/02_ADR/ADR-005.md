# ADR-005 — CI/CD Pipeline Security Gates (SAST + SCA Thresholds)

**Status:** `Proposed`
**Date:** 2026-06-30
**Deciders:** SEP490-G8 Architecture Team (HuyBQHE180599, NamNVHE180863, MinhTTHE186258, ThaoNPHE182154, ManhNDHE160692)
**Context tags:** #cicd #devsecops #sast #sca #github-actions
**US References:** —
**BR References:** `BR-163`, `BR-164`

---

## Context — Bối cảnh

`ADR-001` đã chọn GitHub Actions cho CI/CD và liệt kê Semgrep (SAST), Trivy (SCA — container + dependency), OWASP Dependency-Check (SCA) là công cụ trong pipeline, nhưng **chưa định nghĩa ngưỡng (threshold) cụ thể nào để pipeline fail/pass**. ADR này định nghĩa security gate cụ thể.

**Ràng buộc nghiệp vụ:**
- **BR-163**: Mã nguồn phải được quét lỗ hổng bảo mật trước khi deploy (SAST/SCA bắt buộc trong pipeline).
- **BR-164**: Có ngưỡng (threshold) cụ thể để chặn merge/deploy khi phát hiện lỗ hổng nghiêm trọng.

**Vấn đề cần giải quyết:**
1. Mức độ severity nào (Critical/High/Medium/Low) sẽ **chặn** pipeline (fail build) so với chỉ cảnh báo?
2. Áp dụng gate ở bước nào (PR vs merge vào main vs trước khi build Docker image)?
3. Xử lý false positive như thế nào để không làm chậm tiến độ đồ án (deadline cố định)?
4. Container image (Docker) cần quét riêng so với source code/dependency không?

---

## Options Considered — Các lựa chọn đã xem xét

| Option | Mô tả | Pros | Cons |
|--------|-------|------|------|
| **A** | Quét tất cả, chỉ cảnh báo (report-only), không chặn pipeline | Không bao giờ chặn tiến độ team | Vi phạm tinh thần BR-164 (cần threshold thực sự chặn); lỗ hổng Critical có thể lọt vào main |
| **B** ✅ | Gate phân tầng theo severity: **Critical/High → fail pipeline** (chặn merge); **Medium → warning + tạo issue tracking**; **Low → report only**. Áp dụng ở PR (Semgrep SAST) và trước khi build image (Trivy + OWASP Dependency-Check) | Cân bằng giữa an toàn và tốc độ phát triển của đồ án; có cơ chế xử lý false positive (suppress có lý do) | Cần thiết lập suppression file để tránh chặn oan do false positive; cần maintain ngưỡng theo thời gian |
| **C** | Zero-tolerance — bất kỳ severity nào cũng fail pipeline | An toàn tối đa | Không thực tế cho team sinh viên với deadline cố định; SCA scanner thường có nhiều low/medium findings ở transitive dependencies không kiểm soát được hết |

---

## Decision — Quyết định

**Chọn Option B**: Gate phân tầng theo severity, áp dụng tại 2 điểm trong pipeline.

### Thiết kế pipeline gate

```
[Pull Request opened/updated]
        │
        ▼
[Job: SAST — Semgrep]  quét source code
        │
        ├─► Critical/High finding → ❌ FAIL pipeline, block merge
        ├─► Medium finding        → ⚠️ Pass nhưng tự tạo GitHub Issue gắn label "security-medium"
        └─► Low finding           → ℹ️ Ghi vào report artifact, không block
        │
        ▼ (nếu PR pass SAST)
[Job: SCA — Trivy (dependency) + OWASP Dependency-Check]
        │
        ├─► Critical/High CVE (có fix version available) → ❌ FAIL pipeline
        ├─► Critical/High CVE (chưa có fix)               → ⚠️ Pass + bắt buộc ghi exception
        │                                                      có lý do trong suppression file
        └─► Medium/Low CVE → ℹ️ Report only
        │
        ▼ (merge vào main, trước khi build Docker image)
[Job: Container Scan — Trivy (image)]
        │
        ├─► Critical/High trong base image hoặc layer → ❌ FAIL, không push image lên registry
        └─► Medium/Low → ℹ️ Report only, theo dõi base image update
```

### Xử lý false positive
- Semgrep: dùng `.semgrepignore` + inline comment `// nosemgrep: <rule-id>` kèm **bắt buộc comment lý do** ngay phía trên.
- Trivy/OWASP Dependency-Check: dùng file suppression (`.trivyignore` / `dependency-check-suppression.xml`) — mỗi entry bắt buộc có comment lý do + ngày review lại (không suppress vô thời hạn).

---

## Rationale — Lý do

1. **Gate phân tầng phù hợp với ràng buộc thời gian đồ án**: chặn cứng Critical/High (rủi ro thực sự cao) nhưng không để Medium/Low findings (thường nhiều và có false positive) làm chậm toàn bộ team.
2. **2 điểm gate (PR-level và pre-image-build)** đảm bảo cả source code lẫn dependency/container đều được kiểm tra trước khi đến môi trường gần production nhất mà đồ án có (Cloudflare Tunnel exposed).
3. **Suppression có lý do + ngày review** ngăn việc lạm dụng suppress để "tắt" gate vĩnh viễn — đáp ứng tinh thần BR-164 là threshold phải có ý nghĩa thực sự.
4. **Không chọn Option C (zero-tolerance)**: không thực tế — SCA scanner thường phát hiện nhiều CVE ở transitive dependencies (gián tiếp) mà team không thể fix ngay (phải đợi upstream), zero-tolerance sẽ khiến pipeline luôn đỏ và mất tác dụng cảnh báo thực sự.

---

## Consequences — Hệ quả

**Positive:**
- Critical/High vulnerability không thể lọt vào `main` hoặc vào Docker image production.
- Medium/Low findings được theo dõi có hệ thống (qua GitHub Issues) thay vì bị bỏ qua hoàn toàn.
- Suppression có audit trail riêng (lý do + ngày) — dễ review lại khi có thời gian.

**Negative (trade-offs accepted):**
- Cần thời gian thiết lập 3 job riêng (Semgrep, Trivy+OWASP, Trivy image scan) trong GitHub Actions workflow.
- Có thể có giai đoạn đầu pipeline fail nhiều do backlog vulnerability hiện có trong dependency cũ — cần dọn dẹp một lần ban đầu trước khi gate có hiệu lực thực tế.

**Risks:**
- **R1**: Quá nhiều Medium finding tạo spam GitHub Issues → Giảm nhẹ: gộp theo batch (1 issue/lần chạy CI, không phải 1 issue/finding), dùng label + dedup theo rule-id.
- **R2**: Critical CVE chưa có fix version chặn pipeline vô thời hạn → Giảm nhẹ: cho phép pass kèm suppression bắt buộc có ngày review lại (ví dụ 2 tuần/lần) để theo dõi khi fix version ra mắt.
- **R3**: Team thêm `nosemgrep`/suppression tùy tiện để "né" gate mà không có lý do chính đáng → Giảm nhẹ: bắt buộc code review phải kiểm tra mọi suppression mới trong PR diff (không chỉ kiểm tra code logic).

**Compliance Impact:**
- `BR-163` — Mọi PR và mọi image build đều đi qua ít nhất 1 trong 3 lớp quét (SAST, SCA, container scan) trước khi đến gần production.
- `BR-164` — Threshold cụ thể: Critical/High = block, Medium = track, Low = report — đây chính là "threshold" mà BR-164 yêu cầu, không còn mơ hồ.

**Decisions unlocked (ADR tiếp theo có thể viết):**
- `ADR-XXX`: Quy trình xử lý incident khi Critical CVE được phát hiện sau khi đã deploy (không chỉ chặn lúc CI).

## §AI Prompt Constraint ⭐ CASE 2.0 — BẮT BUỘC

```
Theo ADR-005 (CI/CD Pipeline Security Gates):

1. GitHub Actions workflow PHẢI có job Semgrep SAST chạy trên mọi Pull Request.
   Finding severity Critical hoặc High PHẢI làm job exit non-zero (fail pipeline) —
   KHÔNG được set continue-on-error: true cho job này.

2. PHẢI có job riêng chạy Trivy (dependency scan) + OWASP Dependency-Check trước khi
   merge vào main. CVE Critical/High có fix version available PHẢI fail pipeline.
   CVE chưa có fix version CHỈ được pass nếu có entry trong suppression file kèm
   lý do và ngày review lại.

3. PHẢI có job Trivy container/image scan chạy SAU khi build Docker image và TRƯỚC
   khi push image lên registry hoặc deploy. Critical/High finding trong image
   PHẢI chặn việc push/deploy.

4. Mọi suppression (.semgrepignore, .trivyignore, dependency-check-suppression.xml)
   PHẢI có comment giải thích lý do và ngày tạo ngay tại entry đó — KHÔNG được thêm
   suppression không có lý do kèm theo.

5. KHÔNG được hạ severity threshold (ví dụ đổi Critical/High thành "report only")
   để "làm xanh" pipeline khi gặp deadline — nếu cần ngoại lệ tạm thời, PHẢI dùng
   suppression file có ngày review lại, không sửa cấu hình gate chung.
```
